# Inventory backend

NestJS API and Prisma setup for the InventorySystem frontend.

## Requirements

- Node.js 20 or newer
- A running MySQL database

## Setup

1. From this directory, install dependencies:

   ```sh
   npm install
   ```

2. Copy `.env.example` to `.env`. Set `DATABASE_URL` to your MySQL connection string and set `PGC_SSO_PROJECT_KEY` to the project key issued by PGC SSO. Keep the project key on the backend; never put it in the Angular app.
3. Start the API in development mode:

   ```sh
   npm run start:dev
   ```

The API listens on port `3000` by default. `GET http://localhost:3000/api/health` returns the service health status. Prisma connects to MySQL on its first database query, so SSO login and health checks can run while the database is unavailable. Set `PORT` to change the port, or `FRONTEND_ORIGIN` to a comma-separated list of allowed frontend origins, including your Ionic/Capacitor origin when running on a device.

## PGC SSO login

- `POST /api/auth/login` accepts `{ "username": "...", "password": "..." }` and proxies the credentials to PGC SSO. The project key is sent only from the backend as `X-PGC-Project-Key`.
- `POST /api/auth/validate`, `POST /api/auth/me`, and `POST /api/auth/logout` require the SSO-issued `Authorization: Bearer <access_token>` header. The backend validates the token with PGC SSO before serving these routes.

Configure `PGC_SSO_URL` and `PGC_SSO_PROJECT_KEY` in `backend/.env`. The backend defaults the SSO URL to `https://sso.cagayan.gov.ph` and rejects non-HTTPS SSO URLs.

## Inventory stock-in

- `POST /api/inventory/stock-in` accepts the item name, category, unit of measurement, optional brand and expiration date, quantity, and reorder level. It requires a valid SSO bearer token.
- `GET /api/inventory/stock` returns the 100 most recently added records and also requires a valid SSO bearer token.
- Stock numbers are generated as `YYYY-NNN-BBBBBBBBBB`: the sequence increases per year, and the final ten-digit barcode is generated by the backend. Both stock number and barcode are unique in MySQL.
- Apply the inventory schema migration with `npm run prisma:deploy` after configuring and starting MySQL.

## Item setup and converted inventory

The additive `20261024000000_item_setup_roles_and_movements` migration creates the item catalog, per-item balance, append-only movement ledger, and inventory role allowlist. It adds a nullable catalog relation to `StockItem`; existing stock-in rows are not linked, rewritten, or included in new balances. Do not apply the migration to production until the seeded superadmin employee number and deployment target have been reviewed.

- `GET /api/inventory/items` supports `search`, `category` (`CONSUMABLE`/`NON_CONSUMABLE`), and `status` (`ACTIVE`/`INACTIVE`) filters. Any assigned inventory role can view items.
- `POST /api/inventory/items` and `PATCH /api/inventory/items/:id` create and update catalog items, including an optional brand; ADMIN and SUPERADMIN are required. Conversion factors must be positive, and same-unit items require a factor of 1. Unit or factor changes are rejected after the item has movement history.
- `POST /api/inventory/receipts` accepts `{ "itemId": 1, "quantity": 10 }` in the item's purchase UOM, with optional `expirationDate`. Receipt quantities allow up to three decimal places to preserve the existing stock intake column's precision. It converts to the distribution UOM at six-decimal balance precision, adds the converted amount to the balance, preserves the purchase quantity, and records a movement.
- Stock In copies the catalog brand onto each receipt record. Expiration date is optional per receipt batch; the UI requests a date only when the user checks that the received stock expires.
- `POST /api/inventory/stock-out` accepts `{ "itemId": 1, "quantity": 3 }` in the distribution UOM. The backend atomically rejects quantities greater than the available balance and records the result in the movement ledger.
- `GET /api/inventory/balances` returns catalog items with their current distribution-unit balances.
- The original `POST /api/inventory/stock-in` contract remains available for legacy clients. It does not populate the new catalog balances or movement ledger.

## Transactions and reports

The additive `20261025110000_inventory_workflows_and_reports` migration expands movement types with returns, adjustments, damage write-offs, and physical-count variances. It adds movement notes and physical inventory session/count tables without modifying existing stock records.

The additive `20261025150000_add_item_brand` migration adds an optional brand to catalog items. Existing catalog items remain valid with a `NULL` brand.

- `POST /api/inventory/returns` adds returned distribution-unit quantity to stock and requires a reason.
- `POST /api/inventory/adjustments` accepts `INCREASE`, `DECREASE`, or `DAMAGE`, a distribution-unit quantity, and a reason. Decrease/damage transactions are rejected if they would make the balance negative.
- `POST /api/inventory/physical-count` accepts count lines for every active catalog item plus an optional note. It records expected/count/variance snapshots, applies count variances atomically, and rejects stale counts if the balance changed during counting.
- `GET /api/inventory/movements` returns the newest 500 audited movements and supports optional `type`, `itemId`, `from`, and `to` filters.
- `GET /api/inventory/reports/:report` supports `summary`, `stock-in`, `stock-out`, `low-stock`, `physical-count`, `damage-and-expired-items`, and `transaction-history`. Reports include date filters where relevant.
- Historical stock-in entries created through the legacy endpoint remain visible in stock-in and transaction history. Expired-item reporting identifies receipt records with past expiration dates; their original received quantities are historical values, not a batch-level estimate of remaining stock.

## Inventory access roles

Inventory access is restricted to SSO employee numbers listed in `InventoryRole`. The migration seeds employee number `0000004457` as SUPERADMIN as explicitly configured for this installation. SUPERADMIN can manage role assignments through `GET/POST /api/inventory/roles`, `PATCH /api/inventory/roles/:id`, and `DELETE /api/inventory/roles/:id`. ADMIN and SUPERADMIN can manage catalog items; any assigned role can perform inventory transactions. `/api/auth/validate` now checks for an inventory role, so the migration must be deployed and an administrator assigned before users can enter the protected application.

To deploy after reviewing the migration and confirming the MySQL target:

```sh
npm run prisma:deploy
npm run build
```

The migration intentionally does not backfill balances from historical records. Existing rows remain intact and historical balances are not retroactively inferred. New receipt/issue activity is captured in the new balance and ledger tables.

## Prisma

The Prisma schema is at `prisma/schema.prisma`. Prisma Client is generated after installation and can be regenerated with:

```sh
npm run prisma:generate
```

Create and apply additional development migrations with:

```sh
npm run prisma:migrate -- --name init
```

Deploy existing migrations in production with `npm run prisma:deploy`. The Prisma service is available for injection throughout the NestJS application.
